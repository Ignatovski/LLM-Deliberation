## Independent Merged Assessment

### Summary

The evidence packet describes two interacting vulnerabilities: a confirmed Reflected XSS on the `/displayname` page (L003–L006) and a password-change endpoint protected only by a weak Referer-based check (L010–L011). The critical finding is that the password-change functionality is vulnerable to **CSRF** because the Referer check is trivially bypassed by leveraging the existing Reflected XSS.

### Mechanism

1. The Reflected XSS (L003–L006) allows an attacker to inject arbitrary JavaScript that executes in the application's origin context.
2. When the injected script fires a request from the application page, the browser attaches a Referer header containing the application's own domain (L007).
3. The password-change endpoint (L009) relies solely on `stripos($_SERVER['HTTP_REFERER'], $_SERVER['SERVER_NAME'])` (L010) to validate request origin.
4. Since the XSS-triggered request carries a legitimate Referer, this check passes, allowing an attacker to change an authenticated user's password without their consent — achieving account takeover.

### Severity Rationale

- **High**: Unauthorized password change leads directly to account takeover. The attack requires only that a victim click a crafted link while authenticated. No additional preconditions beyond the already-confirmed XSS are needed.

### User Assumption Verdict

The tester's assumption is **Wrong**. The Referer-based CSRF protection is not sufficient — the existing Reflected XSS enables JavaScript execution within the application's origin, producing requests with a valid Referer that bypasses the check (L007, L010). Therefore, the password-change functionality is vulnerable to CSRF, and there is an additional exploitable vulnerability beyond the known XSS.

Scratchpad (Private)
Let me analyze the evidence packet carefully.

**Understanding the scenario:**

1. L001-L006: There's a confirmed Reflected XSS vulnerability on the `/displayname` page via the `name` URL parameter. Payloads like `<img src=q onerror=prompt(8)>` execute JavaScript.

2. L007: When the injected script executes on the `/displayname` page, requests triggered from that page include the header `Referer: http://webapp/displayname` — meaning the referer points to the application's own domain.

3. L008-L009: There's a password change functionality that uses GET parameters (no anti-CSRF token visible).

4. L010-L011: The password change logic has a "CSRF protection" that checks if the Referer header contains the server name. The check is: `stripos($_SERVER['HTTP_REFERER'], $_SERVER['SERVER_NAME']) !== false`.

**Key insight — CSRF bypass via XSS:**

The referer-based CSRF protection can be bypassed because:
- The XSS on `/displayname` allows an attacker to inject JavaScript that runs in the context of the application.
- When that JavaScript makes a request to `/changepassword?password_new=...&password_conf=...&Change=Change`, the browser will include a `Referer` header pointing to the application's own domain (as confirmed by L007).
- Therefore, the `stripos` check on the Referer will pass, because the Referer will contain the server name.
- This means the attacker can craft a URL that, when opened by a victim, will first execute the XSS payload, which then triggers the password change request — effectively performing a CSRF attack.

The referer check is weak because:
1. It can be bypassed via the existing XSS (the script runs in the app's origin, so the Referer naturally includes the server name).
2. The `stripos` check itself is weak — it just checks if the server name appears anywhere in the Referer string, which could also be bypassed by crafting a Referer like `http://attacker.com/webapp/...` if the server name is generic.

**What's the primary finding?**

The tester's assumption is that the password change is safe because of the referer check, and that the only vulnerability is the known XSS. This is WRONG.

The combined XSS + weak referer check creates a CSRF vulnerability. The XSS allows executing arbitrary JavaScript in the application context, which can then make requests to the password change endpoint. Since those requests originate from a page on the application, the Referer check passes.

So the primary finding here is CSRF — the password change functionality is vulnerable to CSRF because the referer-based protection can be bypassed via the existing reflected XSS.

**Ranking findings:**

1. **CSRF** (High) — The password change endpoint's referer-based protection is bypassable via the reflected XSS. An attacker can craft a URL that exploits the XSS to trigger a password change request that passes the referer check. This allows unauthorized password changes for any user who clicks the link. Citations: L009, L010 (the vulnerable password change mechanism and the weak referer check).

2. **XSS_Reflected** (Medium) — Already confirmed reflected XSS on `/displayname` via the `name` parameter. Citations: L003, L004.

3. **BrokenAccessControl** (Info) — The password change uses GET parameters which could lead to credential leakage in logs/history, but this is secondary. Citations: L009.

Wait, let me reconsider. The XSS is already known. The real new finding is the CSRF. Let me think about severity.

CSRF on password change = High severity. An attacker can change any authenticated user's password by sending them a crafted link. This leads to account takeover.

Actually, let me reconsider the rank-1 label. Is it CSRF specifically? The mechanism is that the CSRF protection (referer check) is insufficient because it can be bypassed through the XSS. The core new vulnerability is CSRF — the password change lacks adequate CSRF protection.

The referer check is a form of CSRF defense, but it's weak. Combined with the XSS, it's completely bypassable. Even without the XSS, the `stripos` check is weak (could be bypassed by including the server name in the attacker's domain/URL).

**Rank 1: CSRF** — The password change functionality is vulnerable to CSRF. The referer-based protection (L010) is bypassable, particularly via the existing reflected XSS (L003-L007) which causes requests to carry a valid Referer header (L007). This enables account takeover via password change.

Severity: High — password change without user consent = account takeover.

**User assumption verdict: Wrong** — The referer-based check does NOT make the password change safe. The reflected XSS allows JavaScript execution in the application context, making requests that naturally pass the referer check (L007). Thus, the CSRF protection is ineffective, and there IS another vulnerability beyond the XSS.

Let me finalize the assessment:

Accept: true — The rank-1 finding of CSRF with High severity is defensible:
- Technically correct: The referer check in L010 is bypassable via XSS (L003-L007 establish the XSS, L007 shows the referer passes)
- Evidence-supported: L009, L010 show the password change mechanism and its weak protection; L007 demonstrates the referer bypass path
- Impact-calibrated: High severity is appropriate for account takeover via password change

All three lenses agree. Accept = true.
